# Контракт интеграции RAG — для Кати

Для интеграции договорились об **одном Python-модуле**, а не отдельном HTTP-сервере.

## 1. Точка входа

Файл: `backend/rag/pipeline.py`.

В нём должна быть доступна функция:

```python
def answer_question(question: str) -> dict:
    ...
```

Можно реализовать как `async def` (адаптер поддерживает оба способа):

```python
async def answer_question(question: str) -> dict:
    ...
```

Не менять имя и обязательный аргумент функции без согласования с backend.

## 2. Вход и выход

**Вход:** `question` — непустая строка с вопросом пользователя на русском языке. Backend уже проверил длину (не более 4000 символов) и убрал пробелы по краям.

**Выход:** Python-словарь с двумя обязательными полями `answer`, `sources` и одним необязательным полем `recipe`:

```python
{
    "answer": "Можно приготовить пасту с грибами...",
    "sources": ["D01", "D05"],
    "recipe": {
        "title": "Паста с курицей",
        "image_url": None,
        "calories_kcal": 540,
        "protein_g": 32,
        "fat_g": 18,
        "carbs_g": 58,
        "cooking_time_minutes": 30,
        "ingredients": ["Курица — 200 г", "Паста — 150 г"]
    }
}
```

- `answer`: непустая строка с окончательным текстом ответа LLM.
- `sources`: `list[str]` с ID рецептов/документов, на которые опирается ответ. Если подходящих документов нет — пустой список.
- `recipe`: **необязательное** структурированное описание одной карточки рецепта из `docs/Product/interface.md`. Его можно не возвращать (или вернуть `None`) — backend будет работать с двумя обязательными полями, как раньше. Для завершённого интерфейса лучше передавать название, изображение (URL), калории, БЖУ, время и ингредиенты. Не выдумывать несуществующие данные: недоступные числовые поля и картинку указывать как `None`.
- Формат ID согласуйте с корпусом и бенчмарком (`D01`–`D30` — удобный пример из занятия).
- Если ответа нет в корпусе, `answer` должен **прямо сообщать**, что подходящих сведений не найдено; `sources` должен быть пустым, `recipe` — отсутствовать или быть `None`. Не придумывать рецепты или источник.

Если библиотека выбрасывает исключение, backend вернёт HTTP 503. Если вернулась неверная структура — HTTP 502. Сохранения частичного ответа в историю не произойдёт.

## 3. Что делает RAG

Катя самостоятельно реализует:
1. Чтение корпуса рецептов и получение идентификаторов.
2. Обработку текста (`re`, `pymorphy3`, `collections`).
3. Собственный поиск BM25 и сборку подходящего контекста.
4. Вызов LLM и генерацию ответа на основе найденного контекста.
5. Бенчмарк согласно требованиям КТ2.

**Требование к запуску бенчмарка:** добавьте запускаемый модуль `backend/rag/benchmark.py`, чтобы в терминале из папки `backend/` команда `python -m rag.benchmark` в реальном времени выполняла 15 запросов, выводила результаты и четыре метрики (Recall@k, MRR, Accuracy, Correct Rejection Rate). Это пока задача Кати, а не готовый скрипт. Для Recall@k/MRR используйте **ранжированный список BM25**, не только поле `sources` итогового ответа. Метрики рассчитываются по заранее подготовленным 30 документам, 10 обычным вопросам с минимум тремя релевантными документами и 5 вопросам-ловушкам. Глубину `k` и MRR согласуйте с преподавателем.

Внешняя API-структура не зависит от выбора внутренних библиотек и механизма доступа к LLM.

## 4. Как backend вызывает функцию

`app/rag_adapter.py` импортирует `from rag.pipeline import answer_question` и вызывает функцию, изолируя синхронный код от event loop при необходимости. Результат валидируется Pydantic-схемой `RagAnswer`.

Из FastAPI использованы **два варианта**:
- `POST /ask` → запрос → ответ, **без** записи в историю;
- `POST /chats/{chat_id}/messages` → запрос → ответ → запись обоих сообщений в SQLite.

### Примечание

Текущая `rag/pipeline.py` — **заглушка**. Замените тело функции, не меняя имя и поля результата. На нынешнем этапе история переписки RAG не передаётся — для контекстных диалогов контракт нужно будет расширять отдельно.
